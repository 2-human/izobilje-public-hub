# proposal-hub composition — Izobilje Hub

Source of truth: `organization-template/library/features/proposal-hub/` (`chassis_version: 2.0.0`).
Composed as **chassis-config**: the chassis was copied unedited (with one recorded exception)
and everything instance-specific is expressed in `content.js`.

This is the first `proposal-hub` instance in the ecosystem that is **not a pitch**. Izobilje is an
umbrella brand, and the hub's function is to hold the architecture and relationships between every
asset the community develops. That difference is carried entirely in config; no chassis behaviour
was changed for it.

## Chassis divergence (two lines)

`index.html` is `hub.html` with two changes. Reproduce with
`diff library/features/proposal-hub/hub.html public/hub/index.html`.

**1. A noindex meta (added).**

```html
<meta name="robots" content="noindex">
```

The hub carries working material (audiences, decisions, roadmap) and was scoped as unlisted. A
`robots.txt` cannot do this job here: the surface is served from a GitHub Pages **project** path
(`/izobilje-public-hub/`), and crawlers only read `robots.txt` at the domain root, which this repo
does not control. Chassis 2.0.0 exposes no `robots` config key, so a static meta is the only
reliable signal. Credo's hub carries the same edit independently, which is evidence the need is
general rather than local.

**Backport candidate 1:** add an optional `robots` key to the config schema so a surface can
declare `noindex` without touching the chassis.

**2. The static `<title>` (changed from `Proposal hub` to `Izobilje Hub`).**

The chassis assigns `document.title` from `HUB.title` at runtime, so the browser tab was already
correct, but the served HTML kept the chassis default. Link unfurls (Slack, WhatsApp, email) read
static HTML and never run the script, so sharing this hub announced it as "Proposal hub" — the one
word this surface is specifically not. Caught on the live response during post-publish verification.

**Backport candidate 3:** have the chassis ship a neutral static `<title>` (or none), since the
runtime already owns the real one and the shipped default is both pitch-shaped and wrong for any
instance that reads it before JS.

## Config-side workaround (no chassis edit)

Chassis 2.0.0 writes `"Proposal for <b>…</b>"` into `#hubProposal` at load, and that string is not
configurable, although the document title next to it *is* (`HUB.title`). For a hub that is not a
proposal the wording is simply wrong. Rather than take a second divergence, `content.js` corrects
that one node on `DOMContentLoaded`, which fires after the chassis IIFE has run.

The hook is guarded on `typeof document.addEventListener === "function"`, not on `document`,
because `validate-content.mjs` loads the config in a vm sandbox whose document stub is `{title:""}`
and would otherwise throw.

**Backport candidate 2:** promote the lede to config (for example `brand.lede`, defaulting to
`"Proposal for <b>{proposalFor}</b>"`), which would remove the workaround and make the chassis
honestly generic rather than pitch-shaped.

## Project inputs

- **Brand tokens** are the live site's own palette (`--forest`, `--honey`, `--cream`), converted
  from HSL, so the hub and izobilje.com read as one brand. Fonts are the site's Lexend/Inter pair.
- **Website artefact** is embedded **by reference**: `WEB` points at
  `https://2-human.github.io/izobilje-public-main-website/` rather than a copy under
  `public/hub/website/`. The hub therefore cannot drift from the real site, and 20MB of imagery is
  not duplicated into a second repo.
- **Required stubs:** `social: []` and a minimal `PF` are present although no social view ships.
  The chassis runs `renderSocial()` on load and throws without them, and
  `validate-content.mjs` does **not** catch it.
- **`STAGES`** is a forward-looking membership/enquiry pipeline. No CRM view ships in v1.
- **No logo mark.** The chassis renders the sidebar logo through
  `filter: brightness(0) invert(1)`, which assumes a monochrome asset with transparency. The only
  logo Izobilje has is an opaque JPG photograph, which the filter flattens into a solid white
  block, so the sidebar runs as a wordmark instead. Supplying an SVG or an alpha PNG and restoring
  one line in `agency` fixes it.

## Views

Six sections, eight views: `intro`, `who`, `audiences`, `website`, `contact`, `planting`, `qamap`,
`decisions`.

The `qamap` view is an inline-SVG question-to-answer map over the Instagram inquiry clusters, with
the nine answers written out beneath it. Each question node links to its answer using the chassis's
own `#view=param` route convention (`#qamap=species-method`) rather than a bare `#qa-…` anchor: the
router ignores unknown hashes, so a bare anchor would leave the view unresolved on reload, while the
param form keeps the view, survives refresh and stays shareable. A small hook in `content.js`
consumes the param and scrolls, since the chassis parses the param but does not act on it.

Each answer carries **every** comment mapped to it, inside a `<details>` disclosure that is
collapsed by default. Native `<details>`/`<summary>` implements the ARIA APG Disclosure pattern in
the browser (`aria-expanded`, Enter/Space, focus) with no custom JavaScript, so the accessible
behaviour is the platform's rather than something to maintain.

Counts are derived from the same extraction that builds the lists, so the map badge, the nav badge
and the number of items in the disclosure cannot drift apart. 42 comments across 9 clusters. The design follows `~/work/library` rather than taste:

- **Schema.org** models this exactly — `Question` is a subclass of `Comment`, carrying `text`,
  `upvoteCount` and `discussionUrl`. The block is shaped to that model so it can be emitted as
  JSON-LD later without restructuring.
- **HTML spec** — the quote is a real `<blockquote cite="…">` with the source URL in the `cite`
  attribute, not a styled `div`.
- **WCAG 2.4.4 (A)** — link purpose must be clear from the link text, so the links read "Open the
  post on Instagram" and "Open the comment on Instagram", never "here".
- **NNG minimalist design** — the quote is evidence, so it is deliberately subordinate: muted, a
  left rule, smaller than the answer above it. The answer stays the primary object.

Quotes are byte-verbatim, including original spelling and mixed Latin/Cyrillic, and a build check
asserts each rendered quote equals its source string exactly. Silently tidying user-generated text
would misrepresent what was said.

**The comment deep links are CONSTRUCTED**, not returned by the API: `{permalink}/c/{comment_id}/`
is Instagram's format and the ids are real, but the URL cannot be verified while logged out —
Instagram answers 200 to any `/c/<id>/`, including a fabricated one, which was tested. The post
permalink comes from the API and is the dependable link of the two; both are shown.

The SVG sits in its own `overflow-x:auto` box with a 720px minimum width, so on a phone the map
scrolls horizontally at full legibility instead of shrinking its labels to nothing. Note that
`.scroll-x` belongs to the WEBSITE stylesheet, not this chassis; using it here silently produced no
scroll container at all. The `who`
view nests Šumski Mir's four offers as `svc__row` items inside its own entry, so the architecture
reads as a hierarchy (five brands under Izobilje) rather than a flat list of nine names. All are `static`
editorial except `website`, which is an iframe. Adding the next artefact is a `nav` item plus a
`VIEWS` entry plus an `html` key, with no chassis change — the `Emails` section and its `planting`
view were added exactly that way.

### Content language

A content-language switcher is implemented **entirely in config**, with no chassis change. `I18N`
holds one `html` map per language; the language is resolved from `?lng=`, then `localStorage`, then
English, *before* `window.HUB` is built, so the chassis paints the right copy first time with no
re-render and no flash. Switching navigates to `?lng=xx` and keeps the view hash, which also makes a
given language shareable as a link.

`html` is `Object.assign({}, I18N.en, I18N[LANG])`, so a language that is only partly translated
falls back to English per view rather than rendering empty sections. That is what makes it safe to
translate view by view.

**Navigation, toolbar headings and the switcher's own label stay English by decision** — they are
system chrome, not content. Only view bodies translate.

### Emails

Both email views are **generated from one data structure**, not hand-written markup. `EMAILS`
describes each form; `renderEmail(formKey, lang)` builds the view. The model is three levels:

    form  ->  variant (a tab)  ->  sequence (the sends for that variant)

So the contact form is one page with seven variant tabs, the reforestation signup is one page with
one variant, and both use the identical template: form metadata, then per-variant the sequence of
sends. Each send carries a status (`sent` / `draft` / `planned`), a timing, a subject slot, and
either a body or a brief describing what it must contain when written.

**Adding a follow-up is appending one object to `sequence`.** Adding a whole new form is one key in
`EMAILS` plus a nav item. Neither touches markup, the chassis, or the other language layers.

A send whose body is missing in the active language falls back to the language it was actually sent
in and is labelled as such, because a sent email is a record and should not be silently restated in
a language it never went out in. Unwritten sends render as a dashed placeholder carrying their brief,
so a promised follow-up is visible as an obligation rather than absent.

Variant tabs are CSS-only (radio + `:checked ~` sibling selectors in a scoped `<style>`), so nothing
depends on script running after the chassis injects the view. Tabs beat a dropdown here because the
subject taxonomy is itself information and the replies need comparing; past roughly eight variants a
list-and-detail layout would beat both.

Email views are named for the **form** that triggers them, not for the individual send, so a form's
whole sequence lives in one view. `planting` therefore holds sequence 1 today and has an obvious
home for the end-of-September follow-up the email promises. Canonical email copy lives in
`content/email/{slug}/EMAIL.md`; the hub view is a rendering of it.

# review-widget composition — Izobilje Hub

Source of truth: `organization-template/library/features/review-widget/`
(`feature_version: 1.3.0`, packaging `descriptive`). That packaging means the consumer composes
the runtime rather than copying a chassis, so this surface was composed by **cloning the freshest
1.3.0 deliverable in the ecosystem** — `midrata/public/hub/`, which is the same proposal-hub
chassis with the same local-only backend — and re-pointing it at Izobilje. Same released
composition contract, so behaviour matches the pinned version.

## Loaded from config, not from the chassis

`review.config.js` and `review-bootstrap.js` are injected by `content.js` (`async = false` to keep
config-before-bootstrap ordering), **not** by adding `<script>` tags to `index.html`. This is a
deliberate difference from the midrata and credo compositions, which each add two lines to their
chassis copy. Keeping the loader in config holds this hub's chassis divergence at two lines, so a
future chassis upgrade re-applies two lines rather than four.

The bootstrap is inert without `?review=1`: it paints only a floating "Comments" button.

## Backend and namespacing

`FIREBASE_CONFIG` is blank, so comments persist to **localStorage in one browser** — fine for solo
review, not shared between reviewers. This follows the meaning-global and midrata precedent: a hub
ships local-only until the org has its own Firebase. Izobilje is deliberately not pointed at
another client's review database.

The storage keys were renamed `midrata_* -> izobilje_*`. This is **not cosmetic**: every 2-human hub
is a GitHub Pages *project* site on the shared `2-human.github.io` origin, so localStorage is shared
between them and unnamespaced keys would genuinely mix one client's review comments into another's.
The inert `CREDO_*` extension globals were renamed for the same reason.

## Commentable everything

The widget anchors any element carrying direct text, so hub components are commentable by default:
**280 anchors** across the seven reachable views (contact 101, planting 43, who 36, decisions 33,
intro 13, audiences 11, website 1) plus chrome. Three local patches were needed to make that
genuinely *everything*:

1. **`reviewer()` no longer dies when `prompt()` is blocked.** The unguarded `window.prompt` call
   throws in embedded and preview contexts, and the exception aborted widget init before a single
   anchor was placed — the entire review mode failed rather than degrading. Now wrapped, falling
   back to "Anonymous". **Backport candidate 4**, and the most important of the three: it is a
   silent total failure, not a cosmetic gap.
2. **`anchorChrome` config flag.** Site chrome (`nav`, `footer`) is excluded by default because
   identical chrome across many pages would duplicate one comment onto every page. This hub is a
   single page, so there is nothing to duplicate and the exclusion only made the sidebar and footer
   uncommentable. Opt-in flag, default unchanged. **Backport candidate 5.**
3. **The image pass now covers `iframe` as well as `img`.** `iframe` is in `NEVER_ANCHOR`, and
   `anchorEmpty` only bypasses the text gate, so the embedded website — this hub's flagship
   artefact — was the one thing that could not be commented on. The pass anchors the container, as
   it already did for images, with an `embed` prefix. **Backport candidate 6.**

## Not retheme

`review-mode.css` keeps its neutral navy chrome rather than the Izobilje palette. Review UI should
never be mistakable for the artefact being reviewed.
